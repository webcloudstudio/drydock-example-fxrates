### Feature: Rates API

| ID | Story | High-level AC |
|---|---|---|
| API-001 | Report service health | `GET /health` returns status 200 and `{"status":"ok"}`. |
| API-002 | Report stored rate statistics | `GET /stats` reports distinct publication dates, rate count, and first and last dates, with null bounds when empty. |
| API-003 | List currencies with stored rates | `GET /currencies` returns EUR as base and stored currencies in ascending order. |
| API-004 | Get rates for an effective date | `GET /rates/{date}` returns all available rate text for the latest publication on or before the valid requested date, or 404 when none exists. |
| API-005 | Get latest rates | `GET /rates/latest` returns the latest publication's rates and identifies the request as `latest`. |
| API-006 | Convert between currencies | `GET /convert` returns the effective date, echoed amount, six-place half-even rate, and two-place half-even result using exact decimal arithmetic. |
| API-007 | Retrieve currency history | `GET /history/{code}` returns ascending points and exact min, max, and six-place half-even mean, including the defined empty-period response. |

## Planning Instructions

### Delivery Shape

A Python command-line application maintains ECB exchange-rate history in SQLite and serves a FastAPI JSON API through uvicorn. The main flow initializes the store, loads a supplied ECB CSV or fetches and loads the ECB archive, starts the server, and answers health, statistics, currency-list, effective-date rates, conversion, and history requests. Rates remain published text in storage and are calculated with decimal arithmetic.

### Test and Acceptance Strategy

Keep story verification bounded to the capability each story implements. Stub the archive download in automated tests so tests never use the network. Run the staged `sources/run.sh` once as the terminal verification of the complete supplied conformance harness; it covers command output, server health, API status and bodies, and visibility of data loaded while the server is running.

### Sequencing and Dependencies

Implement the rates persistence boundary and CSV validation before loading and data-backed routes. Build command dispatch and initialization before load/fetch flows; fetch depends on the shared load path and archive extraction. Data-backed API routes depend on the repository read capabilities. Implement server operation and validation alongside route delivery. The full supplied harness is terminal and depends on all implementation stories.

### Source Conflicts and Gaps

The API has no human-facing screens. The project type is `api` because the primary product capability is a set of programmatic HTTP endpoints, with a supporting CLI. No conflicting product definitions or unresolved human-owned decisions were found. Authentication is not specified and the routes are described as local service endpoints; no protected resource is established by the source.
