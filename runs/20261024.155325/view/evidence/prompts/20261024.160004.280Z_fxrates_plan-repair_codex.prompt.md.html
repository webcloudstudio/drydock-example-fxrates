1: # Build Instructions: A Currency Rates Service
2: 
3: ## Objective
4: 
5: Build a small web service that keeps the European Central Bank (ECB) euro reference exchange
6: rates and answers questions about them: the rates on a date, a currency conversion, and a
7: currency's history over a period. A command-line tool loads the ECB's published history file into
8: a local database. A JSON HTTP API serves the answers.
9: 
10: ## Stack
11: 
12: Implement in Python 3.11 or newer with FastAPI, served by uvicorn, over SQLite. Tests run under
13: pytest, using FastAPI's `TestClient` for the API. The product is an executable named `fxrates` at
14: the application root.
15: 
16: ## Run Harness
17: 
18: `sources/run.sh` is the scoring entry point. It is supplied, not authored, and is staged verbatim
19: into the application root with the data files. `drydock uat` runs `sh sources/run.sh` from the
20: completed application root and takes its exit code and output as the score.
21: 
22: The harness sets `DATABASE_URL` to a fresh temporary SQLite file, runs `./fxrates init` and
23: `./fxrates load`, starts `./fxrates serve --port <port>` in the background on a free local port,
24: waits up to 30 seconds for `GET /health`, and then runs HTTP requests against `127.0.0.1`. It
25: makes 35 checks. A command check compares exit code and standard output. An HTTP check compares
26: the status code and, for status 200, the JSON body as a value (key order and whitespace do not
27: matter). Standard error and error-response bodies are never compared. The harness never runs
28: `fetch` and uses no network beyond `127.0.0.1`. It prints `PASS` or `FAIL` per check and ends with:
29: 
30: ```text
31: FxRates: NN passed, NN failed (of 35)
32: ```
33: 
34: ## Read-only scoring assets
35: 
36: These files are the exam. Do not modify, rewrite, regenerate, or substitute them:
37: 
38: - `sources/run.sh` — the scoring entry point and its known answers
39: - `sources/eurofxref-hist_2025-01.csv` — the ECB history for January 2025: 22 publication dates,
40:   8 currencies, and an `HRK` column that is `N/A` on every date
41: - `sources/eurofxref-hist_2025-02-03_04.csv` — two further dates, 2025-02-03 and 2025-02-04
42: - `sources/eurofxref-hist_bad.csv` — a valid first row and an invalid rate on its second row
43: 
44: Application code never reads `sources/run.sh` and never embeds an answer. Every value comes from
45: the database.
46: 
47: ## Database
48: 
49: `DATABASE_URL` names the SQLite database file, optionally prefixed `sqlite://`. When it is unset,
50: `DATABASE_PATH` is used, then `data/app.db`. All database access goes through the shipped
51: persistence library and the relational layer generated from `DATABASE.md`. Application code never
52: opens a database driver directly.
53: 
54: One table:
55: 
56: | Table | Columns | Keys |
57: |---|---|---|
58: | `rates` | `date` text `YYYY-MM-DD`, `currency` text, `rate` text | primary key (`date`, `currency`) |
59: 
60: A rate is stored exactly as the ECB publishes it, as text. `0.943` stays `0.943`, never `0.9430`
61: and never a float. Arithmetic on rates uses Python's `decimal` module.
62: 
63: ## Command line
64: 
65: | Command | Behavior | Standard output |
66: |---|---|---|
67: | `fxrates init` | Drops the `rates` table if present and creates it empty. | Nothing. |
68: | `fxrates load <csv>` | Loads an ECB history file (rules below). | `dates,rates`, then the number of dates and of rates stored from the file. |
69: | `fxrates fetch` | Downloads `https://www.ecb.europa.eu/stats/eurofxref/eurofxref-hist.zip`, extracts `eurofxref-hist.csv`, and loads it as `load` does. | As `load`. |
70: | `fxrates serve [--port <n>]` | Serves the HTTP API on `127.0.0.1:<n>` with uvicorn until stopped. Default port `8000`. | Nothing required. |
71: 
72: **ECB history file rules.**
73: 
74: 1. The file is CSV. The header's first field is `Date`, and every other field is a three-letter
75:    uppercase currency code. The ECB writes a trailing comma on every line, and the resulting
76:    empty last field is ignored.
77: 2. Each row is a date (`YYYY-MM-DD`, a real calendar date, not repeated within the file) followed
78:    by one value per currency. The value `N/A` means no rate, and nothing is stored for it. Any
79:    other value must match `[0-9]+(\.[0-9]+)?` and be nonzero.
80: 3. **A rejected file changes nothing.** The whole file is checked before the first write. A row
81:    with the wrong field count, an invalid or repeated date, or an invalid value rejects the file.
82: 4. A rate for a (`date`, `currency`) that is already stored replaces it, so loading the same file
83:    twice leaves the database unchanged.
84: 5. The reported `dates` counts the dates with at least one stored rate, and `rates` counts the
85:    rates stored.
86: 
87: A failing command writes nothing to standard output and one diagnostic line to standard error.
88: `fetch` is never run by the harness. Its tests replace the download with a stub and never use the
89: network.
90: 
91: **Exit codes.** `0` success. `1` operational failure: the file cannot be read, or a `fetch`
92: download fails. `2` usage error: unknown command, wrong argument count, `--port` not an integer.
93: `3` rejected file.
94: 
95: ## HTTP API
96: 
97: Every response is JSON. EUR is the base. A rate is the number of units of a currency per euro, and
98: EUR itself has the implicit rate `1`.
99: 
100: **Effective date.** The ECB publishes on working days only. A request for date `D` uses the latest
101: publication date on or before `D`. If none exists, the response is `404`.
102: 
103: | Request | Status 200 body |
104: |---|---|
105: | `GET /health` | `{"status": "ok"}` |
106: | `GET /stats` | `{"dates": <n>, "rates": <n>, "first": <date>, "last": <date>}`. `first` and `last` are `null` when the table is empty. |
107: | `GET /currencies` | `{"base": "EUR", "currencies": [<code>, ...]}`: every currency with at least one stored rate, ascending. |
108: | `GET /rates/{date}` | `{"date": <effective date>, "requested": <date>, "base": "EUR", "rates": {<code>: <rate>, ...}}`: every currency with a rate on the effective date. |
109: | `GET /rates/latest` | As `/rates/{date}` for the latest publication date, with `"requested": "latest"`. |
110: | `GET /convert?from=<code>&to=<code>&amount=<amount>[&date=<date>]` | `{"date": <effective date>, "from": <code>, "to": <code>, "amount": <amount>, "rate": <rate>, "result": <result>}`. Without `date`, the latest publication date is used. |
111: | `GET /history/{code}[?start=<date>][&end=<date>]` | `{"currency": <code>, "base": "EUR", "count": <n>, "min": <rate>, "max": <rate>, "mean": <mean>, "points": [{"date": <date>, "rate": <rate>}, ...]}` for the publication dates from `start` through `end` inclusive, ascending. Both bounds are optional. With no points, `count` is `0`, `min`, `max`, and `mean` are `null`, and `points` is `[]`. |
112: 
113: **Values.**
114: 
115: - `<rate>` in `/rates`, `min`, `max`, and `points` is the stored text, as a JSON string.
116: - `/convert` `amount` matches `[0-9]+(\.[0-9]+)?` and is echoed as given, as a JSON string.
117: - `/convert` `rate` is `rate(to) / rate(from)`, computed exactly and rounded half to even to six
118:   decimal places, written with exactly six decimals, as a JSON string: `"161.770000"`.
119: - `/convert` `result` is `amount × rate(to) / rate(from)`, computed exactly from the stored rates
120:   (not from the rounded `rate`) and rounded half to even to two decimal places, written with
121:   exactly two decimals, as a JSON string: `"82.01"`.
122: - `/history` `min` and `max` are the stored text of the smallest and largest rate by value.
123:   `mean` is the exact mean rounded half to even to six decimal places, written with exactly six
124:   decimals, as a JSON string.
125: 
126: **Errors.**
127: 
128: | Status | Condition |
129: |---|---|
130: | `404` | No publication on or before the requested date; a `/convert` currency other than EUR with no rate on the effective date; a `/history` currency with no stored rate at all (including `EUR`). |
131: | `422` | A malformed date in the path or query, a malformed `amount`, or a missing required query parameter. FastAPI's request validation produces this status. |
132: 
133: A load that completes while the server is running is visible to the next request.
134: 
135: ## Tests
136: 
137: The completed application provides a POSIX-compatible `bin/test.sh` that runs its own pytest suite
138: from the application root and exits zero only when every test passes. The suite covers each
139: command, each load rule, each endpoint, the effective-date rule, rounding, and each error status,
140: against a real temporary database, with `fetch` stubbed.

Acceptance persistence lifecycle

Acceptance store lifecycle. The DATABASE step provisions and verifies the configured store once. Criteria never replace DATABASE_URL/DATABASE_PATH, create a temporary database, apply DDL, or assume an empty store. The store may hold data before any criterion runs: assert on records the criterion created, or on a count read before setup (after == before + 5), never on an absolute table count.

The acceptance harness owns isolation. It begins one transaction before each Python criterion and rolls it back when the criterion ends, pass or fail. Every database the criterion's process opens joins it: db_session(), the application behind web_client(), and commands run through cli_runner(). Setup, behavior and readback therefore see one another's writes, and none persists; leaving a with db_session() as db: block rolls nothing back. Seed with with db_session() as db: and pass that database into feature operations. Never commit, clean up, or open a transaction.

A criterion that launches a process (subprocess, a server on a port, a shell script) cannot see that transaction. It does not open the store and does not depend on rows it wrote; exercise stored behavior in-process instead. Go criteria use OpenSession(ctx, "") with checked deferred cleanup, which rolls back its own transaction. Go HTTP, CLI and restart criteria use OpenCommittedSession(ctx, "") with a criterion-owned identifier and checked defer cleanup through supported product interfaces. Database acceptance must not be replaced by a project test count: runtime catalog and row-count evidence proves provisioning, feature criteria prove behavior.
