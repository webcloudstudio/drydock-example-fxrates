Build a currency rates service, an executable named `fxrates` at the application root, as
described in `sources/INSTRUCTIONS.md`. A command line loads the ECB euro reference rate history
into SQLite, and a FastAPI JSON API serves the rates on a date, conversions between any two
currencies, and a currency's history with minimum, maximum, and mean.

- Implement in Python 3.11 or newer with FastAPI and uvicorn over SQLite.
- Provide an executable named `fxrates` at the application root, invoked as `./fxrates <command>`.

- Read the database location from `DATABASE_URL`, then `DATABASE_PATH`, then `data/app.db`.
- Store rates as the ECB's published text; compute with `decimal`, never with floating point.

## Story Types

The Manifest is a list of stories. A `type` field is the only variation.

| Type | Contains | Runs |
|---|---|---|
| `foundational` | Foundation and scaffolding | Early; work depends on it |
| `service` | Everything that does work | After its prerequisites |
| `feature` | Acceptance criteria plus assembly and intent; no implementation instructions | After its members |

Foundational work is structure and scaffolding. Standing up S3 and proving the connection is
architecture. Everything S3 subsequently does is a service. Everything that is not architecture is
a service. Services may be reordered only when their declared prerequisites permit it. Much of what source
material labels architecture is service work: the web server and the database are foundation; a
voice service interpreter is a service wearing an architecture filename.

Foundation status derives from the dependency graph, not from a filename prefix. The rule is
*build the foundation that is needed*, not *build all foundation first*.

There is no fourth type. A "foundational service" — voice-to-text, for example — is foundational to
whatever depends on it, which the edges already state more precisely than a label could.

`spike` is not a story type. Research questions are handled by questionnaires before Plan and by the
owning story's `## Questions` section after. `ac` is not a story type: Programmatic Acceptance is
verification the build runs to prove a story is complete. A story is not "built and failed" — it is
built or it is not, so acceptance is a field the story owns and passing is part of the story's own
state transition.

### Feature is an assembly story

A feature is a story that depends on its member stories, carries acceptance criteria, and carries
assembly and intent instructions instead of implementation instructions. Same node, same execution
path, different content shape. When its member stories complete, the feature story runs and is made
to pass like any other story, so integration testing is a real build step rather than an implicit
hope. A feature story runs in a later block after its members have passed their gates.

**Story sizing.** A story is a normal Agile story: 1 to 5 story points. Never a half point — that is

### Authorship versus verification

The model authors relationships, the actual topology (the story dependency graph), the high-level
topology (phases), and Programmatic Acceptance. Drydock verifies all of it, groups blocks, orders
the work, and serializes the Manifest.

The model declares and reviews what each story requires and provides, including source-required
processing order and prerequisites exercised by acceptance. It does not compute the schedule.
Drydock validates the declaration and computes order and grouping.
Contradictions become a deterministic error with a precise message instead of a shape failure.

Use the same exact interface name in a provider's `provides:` and its consumer's `consumes:`.
When an interface has a provider in this plan, the consumer has a direct or transitive `depends:`
path to a provider. External inputs without a provider remain legal. A shared executable alone
does not declare the processing stages behind it; preserve their input/output contracts and
source-required dependency edges. File order is not a dependency.

`drydock plan create` therefore does not emit this file. It emits a flat `TOPOLOGY.md` declaration
carrying the Model-authored fields below — one `## story <id>` heading per governed specification,
no ordering, no `block:`, no `stack_mode:`, no `state:` — and Drydock serializes `MANIFEST.md` from
it. The field semantics in this contract govern both forms.

**Two-topology check.** The high-level and actual topologies must agree: a story in phase 2 cannot
depend on a story in phase 3.

### Phase

`Phase` is Commander instruction on how to build: *build Feature X, then Feature Y*. It is not a
layer chain. The layer stack repeats inside each phase rather than running once across the project —
foundational / database / service / ui, then service / ui, then foundational / service / service /
ui. Commander ordering direction is input the model weighs, not an override applied afterward.

`Phase` describes when a file is built, not the file, so it lives in the Manifest and never in a
Blueprint header.

### Tier

The chain that repeats inside each phase is ordered, and each Rigging file declares its position
with a `**Tier:**` header. A tier is a rank inside a phase — never a phase, never a block.

Tiers 1 to 5 are the foundation. Each holds at most one selected file per kind, each publishes a
contract, and each is built into the one before it.

| Tier | Name | Builds | Holds |
|---|---|---|---|
| 1 | `language` | The tree, the environment, the test runner everything else is built into. | `python.md`, `go.md`, `typescript.md` |
| 2.1 | `platform` · database | The one database, built into that tree. | `sqlite.md`, `postgres.md` |
| 2.2 | `platform` · web server | The one web server. | `fastapi.md`, `flask.md`, `django.md` |
| 2.3 | `platform` · CLI | The one command-line entry point. | `cli.md` |
| 3 | `branding` | The palette, the typography, the voice. | `BRANDING_MAIN.md`, `BRANDING_WEBSITE.md`, `BRANDING_DOCUMENTATION.md` |
| 4 | `interface` | The shared UI shell, built with that palette. | `bootstrap5.md` |
| 5 | `screen-foundation` | The screen idiom, built on that shell. | `ui-flask.bootstrap-client.md` |

Tier 2's three kinds are independent — none is built into another — so 2.1, 2.2 and 2.3 order by

Each foundation is its own story. Tiers describe responsibility; declared dependencies
establish delivery gates between blocks.

### Blocks

A **block** groups independent ready stories to share stack and context files in one agent call.
Drydock computes the groups from the declared graph and measured assembled prompt cost.

- Stories share a topology type, phase, and screen/non-screen work kind.
- Every known prerequisite belongs to an earlier block; selecting a story does not make its
  dependents ready inside the same block.
- Compatible stories share the union of their stack and context files, counted once, within
  configured token limits and minimum savings. Criterion count does not bound a block.
- A started block keeps its members and number for resume; only wholly pending work is regrouped.

### Builder and consumer mode

The model authors the foundational story that stands a stack up. Drydock assigns the
builder/consumer flag from first use in the computed order: by definition the first story using a
stack is the builder and later ones are consumers. Ordering is build-order-global, as compact
substitution already is — not per-block, not phase-based. A builder story receives the full stack
file; a consumer story receives the interface view.

If the model assigned the flag it would be asserting a position in an order it has not computed.
Disagreement is a defect signal, not a tie to break: if the first user of a stack is not a
`foundational` story, an edge or a foundational story is missing and Drydock reports it. Ambiguity
defaults to builder, because consumer-when-it-should-be-builder starves the build agent while
builder-when-it-should-be-consumer merely costs tokens.

## Execution Rules

A story runs only when everything in `depends:` is `closed/verified`.

Programmatic Acceptance runs after the story build and is part of the story's own state
transition: a story that fails its acceptance becomes `closed/failed` and blocks dependent work.
There is no separate acceptance node with independent state.

A `feature` story runs after its member stories close. Its assembly and intent instructions are
made to pass like any other story's, which is what turns integration testing into a real build step
covering the seams between stories where multi-story builds actually break.

`closed/failed` is not terminal. The product owner reopens failed work from the QuarterDeck —
revising instructions, acceptance, or scope interactively — and the decision writer returns it to
`pending` with the revision recorded. Recovery never requires hand-editing the Manifest.

An open `Blocking` Blueprint question projects the story state as `blocked/questions`. That story
and its dependents are unavailable, while independent frontier stories remain buildable. Open `Low`
and `Material` decisions remain visible without gating.

`User Acceptance` entries are Commander review signals and do not block ordinary downstream build
unless modeled as explicit dependencies.

## Specification File Header Format

Every authored Specification file except `METADATA.md` and `README.md` must begin with a typed
header. Operational and generated files (`IDEAS.md`, build plans, analysis outputs, and AC files)
are not authored Specification files.

```markdown
# {FileType}: {ObjectName}

| Field       | Value |
|-------------|-------|
| Version     | YYYYMMDD V1 |
| Description | One sentence summary. |
| Depends On  | FEATURE-SERVICE-CATALOG.md, UI-GENERAL.md |
| Provides    | GET /welcome, GET /welcome/summary |
| Phase       | 2 |
```

**FileType values:** `COMPASS`, `SCREEN`, `FEATURE`, `DATABASE`, `UI-GENERAL`, `ARCHITECTURE`,
`HOMEPAGE`, `CHANGE`

**ObjectName:** Human-readable name matching the file subject (e.g., `Welcome Summary`,
`Service Catalog`).

**Fields:**

| Field | Set By | Required | Description |
|-------|--------|----------|-------------|
| `Version` | Author | Yes | Date + increment: `YYYYMMDD V1`. Every agent write must set this to the current date with the next increment. If the existing version is already today's date, increment the number. Never carry forward a stale date. |
| `Description` | Author | Yes | One sentence |
| `Depends On` | `drydock plan create` | No | Filenames this file requires to exist before build |
| `Provides` | `drydock plan create` | No | HTTP routes or interfaces this file exposes |
| `Phase` | `drydock plan create` | No | Build phase hint (integer); tooling may override |

**Additional optional fields for SCREEN files:**

| Field | Required | Description |
|-------|----------|-------------|
| `Route` | No | The URL this screen is served at |
| `Parent` | No | Parent menu item or `—` |
| `Main Menu` | No | Menu label and position |
| `Sub Menu` | No | Submenu label and position |
| `Tab Order` | No | Tab index within parent, or `—` |

`Depends On` and `Provides` are written by `drydock plan create` — do not edit manually.
`Phase` is written by `drydock plan create` — do not edit manually unless overriding.

**Additional required fields for CHANGE files (`changes/TICKET-NNN-{Name}.md`):**

| Field | Set By | Required | Description |
|-------|--------|----------|-------------|
| `Amends` | Author / `drydock refit` | Yes | The parent Blueprint spec this ticket modifies (e.g. `FEATURE-Copy.md`). `drydock refit` reads this field to resolve dependency inheritance and inject parent context. |
| `Depends On` | `drydock refit` | Yes | Copied from the parent spec's `Depends On` set plus the parent spec filename itself. Do not edit manually. |
| `Scope` | Author / `drydock refit --sources` | Yes | `additive` or `amending`. Governs what the ticket supersedes. |
| `Created` | `drydock refit` | Yes | ISO date the ticket was authored. |
| `Origin` | `drydock refit --sources` | No | The source version this ticket came from, as `<source>@<commit>`. Absent on hand-authored tickets. |
| `Stories` | `drydock refit --sources` | No | The Manifest story ids this ticket owns. When present, `drydock refit` emits exactly these ids and never invents new ones. |

**Scope semantics.** A ticket declares its authority over its parent in one sentence directly
below the header table.

- `additive` — the ticket adds behavior. It supersedes nothing, and every assertion in the parent
  Blueprint remains in force. Sentence: *"This ticket is additive. It supersedes nothing; every
  assertion in `<parent>` remains in force."*
- `amending` — the ticket alters behavior already specified. It supersedes only the sections
  listed under `## Amended Sections`, each of which must exist as a heading in the parent.
  Sentence: *"This ticket amends `<parent>`. It supersedes only the sections named under
  `## Amended Sections`; every other assertion in `<parent>` remains in force."*

An additive ticket must never claim authority over its whole parent: a single added requirement
would otherwise supersede assertions it does not mention and that have already been proven.

## Common Authored Specification Sections

Plan and Build disclosures use the existing `DECISIONS.json` schema. `severity: blocking` is the
only decision gate and blocks only the attached story while its Commander response is absent.
Analyze questionnaire answers are converted to `origin: analyze-questionnaire` records. Commander
responses remain in the same records across replans.

Every authored Specification file ends with these sections, using `- None.` when no entries apply:

```markdown
## Programmatic Acceptance

- None.

## User Acceptance

- None.

## Guardrails

- None.

```

`Programmatic Acceptance` contains executable Python assertion snippets. Each check is one
explicitly delimited block that can run from the build directory after the story implementing the
file completes:

```
=== AC {check-id} ===
Intent: One or two lines stating what the check proves and why its fixtures exercise it.
Suite: scoped
Requires: executable=python3; scope=test
Probe: --list
Probe Count: summary

<Python source, verbatim, to the end marker>
=== END AC {check-id} ===
```

The delimiters are the whole format. The id lives in the opening marker, so it is never inferred
from a nearby heading. Declarations are the `Key: value` lines at the top of the block, ending at
the first blank line; `Intent:` is required and the rest are optional. Everything after that blank
line is the proof body, taken character for character to the matching end marker.

Every criterion declares one or two nonblank `Intent:` lines: the behavior it proves, the expected
relationship, and, where useful, why its example inputs exercise that behavior. A table of cases
shares one explanation. Plan selects the inputs and calculates the expected results from the
specification; those constants need not appear in source material and need no citation. Repair
quotes these lines verbatim, and a failing criterion never authorizes changing its expected result.

`Probe:`/`Probe Count:` are required together whenever the body invokes a staged runner with a
literal selection option (a flag choosing a subset of an imported corpus, such as `--sections` or
`--select`). All runner arguments after the staged script must be statically resolvable: use
string literals or module-level literal string bindings for the product, corpus and selector.
Canonical `os.path.abspath("literal-path")` is supported with an unmodified `import os`.
Do not use getcwd f-strings, dynamic imports or runtime argument construction; they can run in
Python but Drydock cannot use them to prove the selected corpus before Build.
Drydock re-invokes that same runner with all literal arguments, including corpus
paths and selector options, plus the `Probe:` flag(s) appended — flags that make the runner list or count the matched cases with no
candidate present, e.g. `--list`. `Probe Count:` names how to read the probe's stdout: `lines`
(one selected case per non-blank line) or `summary` (the count is the leading integer of the
trailing non-blank line, e.g. `27 cases, 2 excluded`). Drydock runs the declared probe before
build and refuses the plan if the selector proves to match nothing.
Use only flags and output formats the supplied runner actually implements; the `--list` example
is not a default. `Probe Count: json` counts elements of a JSON array, including zero for `[]`.
For a runner whose `--dump-tests` emits a JSON array, declare `Probe: --dump-tests` and
`Probe Count: json`. Never count pretty-printed JSON lines as cases or declare a summary for JSON.
Program and corpus-path options do not select cases. Preserve the criterion's actual section
filter and corpus path when declaring its probe; never change supplied read-only runners to
accommodate a probe protocol.

Put each `Requires:` declaration inside its `=== AC ... ===` block, before the Python body;
repeat it for each criterion that needs it. A declaration before the opener belongs to no
criterion. Selecting a framework in TECHNOLOGY_STACK.md does not declare the criterion's tools. Each criterion declares every imported
external package and its test transport. For FastAPI TestClient on Starlette 1.2 or newer, declare
`fastapi` and `httpx2` with `scope=test`; use `httpx` only for a compatible older selected stack.
Pin the resolved compatible dependency set in the application lockfile. Import every name inside
each criterion, including a criterion re-emitted by artifact repair.
A foundation criterion verifies its factory/client interface without invoking an endpoint owned
by a later service story; endpoint criteria assert the exact required status, never 200-or-404.

Nothing inside the body can move a boundary. A Markdown fence, a `##` line, a `###` line, or a
`Requires:` line inside a string is ordinary content — which matters, because a target that
processes markup will legitimately embed all of them in its proof. Write the body as plain Python;
do not wrap it in a fence.

Generate valid structured input with its standard serializer. For CSV success cases, use
`csv.writer` with `lineterminator="\n"`; do not concatenate or replace quote characters to
construct records. To test trimming and quoting together, pass padded values such as
`"  red, green  "` to the writer so the padding stays inside the quoted field. Spaces outside
quotes are CSV syntax, not decoded value padding. A success criterion follows the source's
parser contract (including RFC 4180 when required); it never demands permissive parsing to
accept a malformed fixture. For a strict CSV source contract, construct malformed records
explicitly only in rejection criteria.

Write `=== END AC {check-id} ===` for every `=== AC {check-id} ===` you open, with the same id.
The end marker is not optional and the next opening marker does not stand in for it. Where the
boundary is decidable Drydock inserts the missing marker and reports having done so; where it is
not, planning stops.

An end marker naming a different id, a stray end marker, and a duplicate id are hard errors that
stop planning. None of them degrade into a criterion that silently stops gating.

A backslash in the proof body belongs in a raw string or is doubled. Write `r"\d+"`, `"\\("`, or
`r"\("` — never a bare `"\("`. A bare backslash before a character Python does not recognize as
an escape is not the escape you wrote: it survives today only by a rule scheduled to become a
hard error, and it costs the criterion its binding status. This applies to every proof that
embeds a regular expression, a Windows path, or a target language's own escape syntax.

### The oracle rule

> **Act on the system. Read the state back. Compare to expected.**

Arrange–Act–Assert, where the assertion reads *state*, never text a process printed.

| Oracle | Verdict |
|---|---|
| Return value, parsed JSON, status code, DB row, file contents read back, exit status | **Correct** |
| Substring of captured stdout/stderr, test-runner tally text, log lines | **Forbidden** |

A state oracle cannot pass against a stub and cannot fail because a runner printed the word
"warning". Almost every acceptance defect observed in practice has the same shape: the oracle was
a string in captured output.

### The expected value must be one you could not get wrong

An expected sequence follows its declared sort keys, including secondary keys and mixed directions.
Derive the expected rows from fixture inputs, then sort by those keys; never copy insertion order
into a sorted-output assertion. For `date asc, currency asc`, `YYY` precedes `ZZZ` on one date.
Plan and verify reject a statically resolvable expected row sequence that contradicts a declared
repository `Order` (`ordered-oracle`). This check does not execute proof code or prove arbitrary
ordering expressions correct. Mechanical `plan repair` preserves these assertions for source-based
authoring rather than choosing a new expected order.

A service-start criterion waits within a fixed deadline for the required endpoint or port at the
configured address. It asserts the source's exact response, fails if the process exits or the
deadline expires, retains startup diagnostics, and terminates and reaps the child in `finally`.
An immediate `Popen.poll() is None` proves only process creation and is rejected as
`process-readiness`. Do not substitute a sleep for a readiness probe or use the probe to require
an endpoint owned by a later story; give the criterion the dependency it actually exercises.


For computed numeric output, derive the oracle from the fixture inputs using the source formula.
Never hand-calculate a formatted decimal answer. Use `Decimal` for decimal contracts, preserve
unrounded intermediate values, and apply the specified rounding only at the stated boundary.
For example, with amount `"2.00"`, source rate `"2"`, and target rate `"5"`:

```
from decimal import Decimal, ROUND_HALF_EVEN
expected = (Decimal(amount) * Decimal(target_rate) / Decimal(source_rate)).quantize(
    Decimal("0.01"), rounding=ROUND_HALF_EVEN
)
assert body["result"] == f"{expected:.2f}"
```

Read `body` from the application response. This oracle is `5.00`; typing `10.00` invents a
requirement. Preserve published text exactly when the source requires a round trip; do not add
rounding or normalization merely to make an oracle look derived. Static analysis reports
unrecognized decimal provenance as an advisory, never as proof of an invalid expectation or a
reason to rewrite it. Known fixture values may be embedded in CSV, JSON, ZIP members or other
serialized inputs. A derived expression is also not proof of a correct formula: source intent
remains the authority. Moving a guessed answer into a variable does not establish correctness.


Reading state back is half the rule. The other half is what you compare it *to*.

> **Never type an expected value twice. Bind it to a name and use the name on both sides.**

You are authoring this criterion before the code exists, so a hand-typed expectation is a
prediction about bytes you have not seen. When the prediction is wrong the criterion fails against
a correct implementation, and nothing downstream can tell that from a real defect. This is the
single largest source of wasted build budget on record.

| Expected value | Verdict |
|---|---|
| A name bound to the value the criterion supplied as input | **Correct** |
| A status code, exit status, or count | **Correct** |
| A contract token read off a declared interface — `"integer"`, `"application/json"`, `"POST"` | **Correct** |
| A staged suite's exit status | **Correct** |
| A string literal you typed out as the expected result | **Forbidden** |

The forbidden row is judged mechanically: a string expectation carrying anything escapable —
whitespace, a backslash, a quote, a newline, a non-ASCII character — that the criterion did not
also supply as input. An expectation assembled in the criterion — an f-string, a `+`
concatenation with a string, `"..." % args`, or `"...".format(...)` — is forbidden the same way,
unless that same expression is what the criterion supplied as input. A criterion that breaks the
rule still runs and is still reported, but it settles `DISPUTED` and gates nothing, so it buys the
story no coverage at all.

One exception is mechanical too. When the source material under `sources/` states the exact
expected value, cite it: `Cite: sources/<file>:<line>` or `Cite: sources/<file>:<start>-<end>`. A
literal that appears verbatim in the cited lines is derived, not re-typed, because the source is
the authority. `drydock plan verify` refuses a citation that does not resolve or whose lines
contain none of the criterion's expected literals.

The case this comes from. Wrong:

```
source = 'basic = "line\\nvalue"\nraw = \'C:\\\\Users\\\\nodejs\'\n'
result = subprocess.run(["./toml-decoder"], input=source, capture_output=True, text=True)
decoded = json.loads(result.stdout)
assert decoded["raw"]["value"] == r"C:\Users\nodejs"     # re-typed, and wrong
```

A TOML literal string preserves its backslashes verbatim, so the decoder returned the doubled
form and the expectation was wrong. Right:

```
raw = "C:\\Users\\nodejs"
source = f"raw = '{raw}'\n"
result = subprocess.run(["./toml-decoder"], input=source, capture_output=True, text=True)
decoded = json.loads(result.stdout)
assert decoded["raw"]["value"] == raw                    # one spelling, cannot disagree
```

The same rule applies when the re-typed value is not a string literal but an independently
reconstructed expression — a rebuilt path, URL, or timestamp compared against one the code under
test computes itself. Two spellings of "the same" value can disagree exactly where a normalization
step is involved (`.resolve()` against a relative join, a trailing slash, case folding), and the
criterion has no way to know which spelling the implementation is entitled to produce. Read the
value back from what the code exposes; do not reconstruct a second copy to compare it to.

Wrong:

```
from pathlib import Path

sources = Path("sources")
import run_conformance
assert run_conformance.CORPUS == sources / "jq.test"     # rebuilt, and not the same path shape
```

`run_conformance.CORPUS` is `Path(__file__).resolve().parent / "jq.test"` — absolute, because the
module resolves its own location. `sources / "jq.test"` is relative. Nothing the implementation
does can make these equal; the criterion is unsatisfiable regardless of correctness. Right:

```
from pathlib import Path

sources = Path("sources")
import run_conformance
assert run_conformance.CORPUS == (sources / "jq.test").resolve()
```

or, when the criterion only needs to know the module points at the right file, assert what it
actually claims rather than reconstructing a value to compare:

```
assert run_conformance.CORPUS.samefile(sources / "jq.test")
```

When a transform's output genuinely cannot be derived from its input — a renderer turning `# h`
into `<h1>h</h1>` — do not hand-write the expectation at all. Bind the criterion to the
authoritative suite that defines correctness for that transform. Where no such suite exists, put
the case in the project's own test suite, where the implementer writes it against real output,
rather than predicting it here.

### Two test destinations

A project carries tests in two places, and they are not the same artifact with different names.

| | **Story AC** — `=== AC <id> ===` | **The project's own test suite** |
|---|---|---|
| Job | gate the block | know the code works |
| Count | few | unbounded |
| Authored | here, by planning, **before the code exists** | by the build agent, **alongside the code** |
| Oracle discipline | the rules above, without exception | full latitude — expectations are observed, not predicted |
| Effect | binding: it decides whether the block closes | diagnostic: it guides repair, and its command is what a project criterion runs |
| Runs | at its block | continuously, cumulatively |

The split is not a matter of taste. Every expected value written here is a *prediction* about
bytes that do not exist yet, and a wrong prediction fails a correct implementation — which is why
the oracle rule and the no-re-typed-literal rule are absolute in this file. A test written beside
the finished code compares against output its author has actually seen, so the same assertion that
is hazardous here is safe there.

So this is *more* testing, not less. Exhaustive coverage belongs to the project's suite, which has
no ceiling. An AC block is permanently constrained by having to survive as a gate, so author few
and author them bulletproof. Coverage is never demonstrated by the number of AC blocks a story
carries; it is demonstrated by the suite, and it is graded at the project level through the Sea
Trial that runs that suite.

**Where an authoritative suite exists, it is the coverage.** A conformance corpus staged into
`sources/` defines correctness for the surface it covers. Bind one criterion to it and do not
restate its cases in either destination — a restated case adds no coverage and adds one more
expectation that can be wrong.

**The terminal story is the last story in the build order** — the one on which every other story
is a transitive dependency and after which no further story runs. It is decided by position in the
graph, never by name, type, or kind. A story is not terminal because it is called "verify", because
its `kind` is a test harness, or because it stages the test assets: staging the corpus is
foundational work that runs first, and running the corpus is terminal work that runs last. When a
plan contains several verification stories, exactly one of them is terminal and it is the one every
other story precedes. Identify it by resolving `depends` before writing any suite criterion.

**Only the terminal story runs the whole suite.** No intermediate story's acceptance invokes the
runner unscoped. A partial capability fails most of an authoritative corpus by construction, so an
unscoped mid-build run reports the schedule rather than a defect — and it is slow in exact
proportion to how incomplete the code is, because unimplemented cases exhaust the runner's per-case
timeout instead of returning. It costs most at the point in the build where it teaches least, and a
build agent that starts one mid-story typically abandons it and reports the suite as hung.

**An intermediate story runs its own slice, and the slice executes.** Scoped to the cases that
story implements, the run is neither slow nor red by construction: those are exactly the cases its
code is supposed to pass, so the result is a verdict about the story rather than a report on the
schedule. This is what makes build progress visible — the corpus goes green in the order the plan
builds it, and a regression in an earlier story is caught by the later story that re-runs it.

A section title is not a prerequisite boundary. Review the supplied selected examples for
cross-feature interactions and preserve the frozen topology's coverage assignments. A nonempty
probe does not establish that every selected capability is available. Use only documented
runner options to select an implementable slice. If the runner supports only a mixed section
that requires future work, test the current story's own API directly (without restating corpus
examples), then assign that entire section to a later integration with all required providers.
That integration runs the real corpus before the terminal gate. No case is dropped, expected
result changed, or dependency cycle introduced; the early gate measures the delivered capability.

Executing is the whole point, so:

- The slice **runs cases**. A criterion that invokes the runner's list or dry-run mode executes
  nothing, passes before the story's code exists, and proves only that the runner starts. Such a
  criterion is a defect: it is green from the first build call to the last and steers no repair.
- The slice is **selected by the story's capability**, using the runner's own scoping flag — not by
  case count, not at random, and never by a selector that silently pulls in cases belonging to
  unbuilt stories. Size and inspect each selector with the runner's list mode **while planning**;
  that is where list mode belongs, not in a criterion.
- Every slice invocation supplies each environment variable the runner declares required.

**Together the slices cover the corpus.** Every case an authoritative suite contains belongs to
some story's slice. A case no intermediate slice reaches is first executed by the terminal gate,
where a failure arrives with the whole build already spent and no story to attribute it to.
Overlap between slices is expected and costs nothing — a case exercised by two capabilities
legitimately belongs to both — but a gap is a story whose work no one checked.

**A story that only stages the suite asserts staging.** Where a story's obligation is that the
corpus parses, the exclusion list applies, and the runner starts — and it implements none of the
behavior under test — its criterion invokes the runner's list or dry-run mode and asserts the
runner exits `0` and reports the expected count. This is the one criterion for which executing
nothing is correct, because there is nothing of the product to execute yet. Leaving such a story
with no criterion at all is a defect: it produces a story that cannot be verified and a build block
that closes advisory.

If an imported instruction states where the suite may run, that statement governs.

### What a criterion is worth

Every criterion you write lands in one of four tiers. The tier is decided by how the criterion is
written, not by how it is labelled, and it decides what the criterion can do:

| Tier | What it is | What it does |
|---|---|---|
| **BLOCKING** | a Commander-governed gate, or a criterion bound to a staged authoritative suite | fails the block |
| **CONSULTATIVE** | a criterion whose expected value could not have been invented — a status code, an exit status, a value the criterion itself supplied as input | drives repair; unattended, it marks the block implemented-but-unverified rather than stalling the run |
| **ADVISORY** | a criterion that re-types an expected literal | runs, is reported `DISPUTED`, **gates nothing** |
| **VOID** | malformed: does not compile, or an unclosed container | not a criterion; recorded as a decision and gates nothing |

Aim deliberately. A hand-typed expectation does not merely risk being wrong — it demotes the
criterion to ADVISORY, so the story it was written to protect ends up with no gate at all. Binding
the value to a name is what buys the criterion its authority back.

None of these tiers reaches the release verdict. Story AC decides whether an increment was built;
project acceptance is decided by Sea Trials alone.

### Authoring patterns

Patterns **1, 4, 6, 9, and 10** are the discipline of a gate and govern what you write here.
Patterns **2, 3, 5, 7, and 8** are the discipline of a test suite: state them as expectations on
the project's own suite, which the build agent grows beside the code, rather than enumerating them
into AC blocks.

**1 — Round trip (the default form).** For anything that stores, mutates, or removes state:

```
create  → read back → assert present, with expected field values
update  → read back → assert changed, and only the intended fields changed
delete  → read back → assert absent
```

The read-back is a *separate call through the public interface*, not an inspection of the object
returned by the write. A write that returns a plausible object while persisting nothing must fail.

**2 — Exercise every callable workflow.** *Suite pattern.* One test per public entry point, per
verb. Coverage is enumerated from the interface, not sampled: every HTTP route × every method it
declares including declared error paths; every CLI subcommand and every flag that changes
behavior; every exported library function. This belongs to the project's suite. Here, name the
routes a SCREEN provides — that gate is real — and leave the enumeration to the suite. Where a
staged authoritative suite already covers the surface, it is the coverage.

**3 — Idempotence.** *Suite pattern.* Where a verb claims idempotence (PUT, DELETE), apply it twice and assert the
second is a no-op — same resulting state, and the declared status for a repeat. Where a verb is not
idempotent (POST), apply twice and assert the declared behavior: two resources, or the declared
conflict. Prefer idempotent verbs where the semantics allow; the assertion is stronger.

**4 — Negative paths assert the contract, not the message.** Invalid input asserts the declared
failure signal — status code, exception type, exit status — never the wording of an error message.
Message text is prose and belongs to no contract.

**5 — Boundaries.** *Suite pattern.* Empty collection, exactly one, many. Absent optional fields.
Declared maxima. This is where a plausible-looking implementation actually breaks — and where a
predicted expectation is most likely to be wrong, which is why the cases belong beside the code
rather than here. Where a staged authoritative suite covers the surface, it is the coverage.

**6 — RED before GREEN.** The assertion must fail against the pre-implementation tree and pass
after. A check that passes against a stub is not a check.

**7 — Isolation and determinism.** *Suite pattern, and it applies here too.* Each test arranges its own data and does not depend on another
test's residue or on ordering. No wall-clock dependence, no third-party network, no unseeded
randomness, no sleep-based timing. Fresh store per test, or explicit teardown.

**8 — One behavior per test, named for the behavior.** *Suite pattern.* A failure should be
diagnosable from the test's name alone.

**9 — Subprocess discipline.** Where a check must shell out, **exit status is the verdict**. A
substring check beside an exit-status assertion is redundant at best and a false-positive generator
at worst. Never assert that a literal is absent from captured output.

**10 — In-language tooling.** A check is written in the project's own language and uses that
language's libraries — Python check, Python libraries; Go check, Go libraries. An in-language HTTP
client yields a status code and a parsed body, which is state. `curl` yields stdout, which is text
to scrape. Pattern 10 and the oracle rule are the same rule seen twice.

### Declaring external tooling

Reaching for an external executable is the exception, not the norm, and `curl` in particular will
not work in every environment. When a check genuinely needs one, the tool belongs in the project's
Rigging or `TECHNOLOGY_STACK.md`, declared once by the Commander and true for every check in the
project. A per-check declaration is also accepted and is recorded as a report:

```markdown
Requires: python-package=httpx2; scope=test
Requires: executable=node; scope=test
```

Kinds are `python-package` and `executable`; scopes are `runtime` and `test`. Framework test
clients include their transport dependencies. `Requires:` metadata is not acceptance intent, and
a missing declaration never fails planning — a tool that is present and undeclared works fine.
A declared tool that is *absent* when the check runs reports UNVERIFIED, not FAIL: the check never
reached the code under test, so it says nothing about the build.

### Satisfiability

Every assertion must be satisfiable by a correct implementation. An expectation no implementation
can meet is a defect, not a red baseline. Escaping is the usual source of one: inside a raw
literal, `\n` and `\r` are a backslash followed by a letter, not a control character, so
`r"text\n"` asserts against six characters ending in a literal backslash. Binding the value to a
name and using it on both sides removes the question entirely, which is why that is the rule.

### Runnability

**Subprocess mode.** Match the mode to `input=`. Text input declares `text=True` or `encoding=...`;
binary input uses a bytes-like value and does not declare `text`, `encoding`, `errors`, or
`universal_newlines`. A mismatch raises `TypeError` before the program under test starts, which
reports UNVERIFIED — the criterion buys the story nothing. Write:

```
payload = "one line\n"
result = subprocess.run(["./program"], input=payload, capture_output=True, text=True)
assert result.returncode == 0
```

For a binary or invalid-encoding criterion, write:

```
result = subprocess.run(["./program"], input=b"\xff", capture_output=True)
assert result.returncode != 0
```

**ASCII test data.** Acceptance data is ASCII. Do not invent an encoding requirement: characters
outside ASCII test a property the specification never stated, and a criterion that fails on them
fails the build for something nobody asked the product to do. When the imported specification does
state an encoding requirement, the criterion says so and may then use that encoding:

```
=== AC runtime-utf8 ===
```

**Stated behavior only.** A criterion asserts behavior the source states, not behavior its phrasing
implies. "Takes no arguments", "has no configuration", and "has no side effects" describe the
surface a program offers; they are not requirements that it detect and reject an argument, a
configuration file, or a write. Where the source supplies a reference implementation, that
implementation bounds what the criteria may demand: a criterion the reference shape would fail is a
criterion the source did not ask for.

**Every check is standalone.** Drydock writes each fenced block to its own script and runs it in
its own process from the build directory. Checks in the same file share no imports, no variables,
and no execution order. A snippet that reads a name another snippet bound raises `NameError` on
every run — it reports UNVERIFIED rather than failing the build, which means it verifies nothing
and buys nothing. Each snippet imports what it uses and binds every name it reads.

**Every check creates the state it depends on.** A check starts from the existing provisioned application store. Before
the action under test, it creates every row, file, or record that its input refers to and that a
source rule requires to exist. A check that loads a transaction for account `A` first loads account
`A`. Without that setup, a correct product rejects the input: an expected success fails, and an
expected rejection passes for the wrong reason. Every setup call asserts the success its source
declares: a valid staged asset loads with exit `0`, never `1`. A setup call that expects failure
creates nothing, and the action under test then runs against the empty application.

Every `cli_runner` invocation asserts its expected exit status before its result is consumed
or another command runs. This includes setup, the action under test, and final readback calls.
Successful setup and readback calls assert exit `0`; rejection calls assert the required rejection
exit. A parsed output assertion never replaces the exit-status assertion.

For example, set up an account, reject a deletion that would make its balance negative, then
read back the account. This excerpt omits fixture details: choose `acct`, create the deposit and
later outflow where indicated, and bind `deposit_id` from the successful deposit result. The
remaining criterion asserts the source-defined unchanged state:

```python
code, out, err = cli_runner("account", "add", acct, "Delete Probe")
assert code == 0
# Create the deposit and later outflow here; assert each setup call's exit is 0.
code, out, err = cli_runner("txn", "delete", deposit_id)
assert code == 3
assert out == ""
code, out, err = cli_runner("account", "get", acct)
assert code == 0
row = parse(out)[1]
```

Incorrect final readback (the exit is unchecked):

```python
code, out, err = cli_runner("account", "get", acct)
row = parse(out)[1]
```

Correct final readback:

```python
code, out, err = cli_runner("account", "get", acct)
assert code == 0
row = parse(out)[1]
```

Before returning each AC, inspect every `cli_runner` call, including the last call and calls
inside loops or helpers. Each exit is asserted before output parsing, output assertions, or the
next command; a helper returning the runner result requires its caller to assert the exit.

**A check exercises the built application through the client its foundation publishes.** The
Rigging file for the Target's web server, database and CLI publishes a `## Foundation Contract`
naming the package, the entry point, and the client callable — `web_client`, `db_session`,
`cli_runner` — a plain function in `<package>/testing.py`. A check imports it from there and calls
it: `from app_server.testing import web_client`, then `client = web_client()`. That runs the
application the build wrote, in-process, without pytest; the pytest suite receives the same
callable through `conftest.py`. The names are fixed by the technology the Commander selected, so a
criterion writes them rather than inventing a package or constructing a client of its own.
Constructing one is how a Blueprint set ends up split between two package names and calling a
framework's method on another framework's object.

A check may also run the application's own pytest suite through the language foundation's
`test_command`. It imports the foundation package before it does, so against an application that
is not built it fails as `foundation not built` rather than inside pytest. A suite run is never a
story's only proof: the builder writes those tests, so at least one check asserts behavior the
Blueprint states.

A check importing a foundation package the build directory does not contain is not run and fails
as `foundation not built`. That is the expected red before the foundation story builds it.

`app_server`, `persistence`, and `cli` are reserved: each names the selected foundation of that
kind, whichever file the Commander selected. A criterion importing one the stack did not select,
or importing a published entry point from any other package, is refused as `unknown-package` and
the plan is written `unbuildable`.

**A check never reads a Blueprint document.** The Blueprint is the build's *input*; the build
directory holds the code written from it and nothing copies a specification next to that code.
`pathlib.Path("ARCHITECTURE.md").read_text()` raises `FileNotFoundError` on every run, so no
implementation and no repair pass can turn it green. It is also worthless where it succeeds:
grepping a specification for the words it was written with asserts that the document contains
itself, and passes against an empty build directory. Assert against the built artifact — import
the module, call the route, read the value off the settings object. Only paths under `sources/`
are staged into the build and may be named. `drydock plan verify` refuses a criterion that reads
one, and the plan is written `unbuildable`.

**A check that shells out prints what it captured before it asserts.** `capture_output=True`
routes the runner's tally and its failing cases into a variable; asserting on the exit code alone
then discards them, and the failure reports the assertion with no evidence of what went wrong.
Print the captured `stdout` and `stderr` first, so the console, the evidence file, and the repair
pass all carry the runner's own account of the failure. Printing is for diagnosis; it is never the
oracle.

**A check that drives a suite prints its tally.** A criterion answers one yes-or-no question, so a
run that fixes a hundred cases and a run that fixes none report the same failure, and the build
reads that as a stalled repair and stops paying for calls that were working. The count is what
separates them. Where the runner reports a machine-readable summary, parse it and print the
counts on one line before asserting:

```
report = json.loads(result.stdout)
summary = report["summary"]
print(f"{summary['pass']} passed, {summary['fail']} failed, {summary['error']} errored")
assert summary["fail"] == 0 and summary["error"] == 0
```

Print the counts even when the criterion asserts on the parsed object rather than on the text.
Requesting `--json` and asserting straight off the parsed report leaves nothing on either stream,
and a suite of hundreds of cases then reports its progress as a single bit.

`User Acceptance` contains only Commander-observed checks that cannot be honestly automated,
such as look-and-feel or subjective workflow acceptance. Do not place deterministic behavior in
`User Acceptance`.

Do not tag an assertion with a project-acceptance ID. Sea Trials flow into planning as context for
authoring acceptance; nothing points back at them. Project acceptance is settled at `score release`
by observing the finished tree, never by looking up which assertion claimed which criterion.

**Programmatic acceptance is the story's definition of done, and a deterministic definition of
done is never sampled.** Drydock builds each block in a single pass with no iterate loop, so the
acceptance you author *is* the objective handed to the builder: sample the checks and the builder
builds to the sample. When an authoritative, externally-authored test suite already defines
"correct" for what a story builds — an imported conformance suite and its runner (for example a
specification's example suite plus a `*_tests.py` runner) — the acceptance runs that suite and
requires a full pass over the story's scope, never a hand-picked subset. A feature story binds to
the sections it owns and declares `Suite: scoped`; a terminal verification story gates on the whole
suite and declares `Suite: full`. The marker is one of the block's declaration lines and tells the
runner the check gates on the whole test suite rather than a story-scoped sample.

**A scoped selector must select something.** A check that runs a suite with a section filter
matching no cases exits zero and reports a pass while proving nothing. Select on a heading that
actually owns cases, never on a chapter title that merely contains such headings. Drydock fails a
criterion that is already green before the story's code exists. This is checked mechanically, not
only reasoned about: declare `Probe:`/`Probe Count:` for every such selector, and Drydock runs the
declared probe before build and refuses the plan if it counts zero.
**The runner's exit status is the verdict, and it is the whole verdict.** A conformance runner
already decides pass or fail and reports it the one way a caller can rely on. Asserting on its
printed summary as well adds no information and adds a failure mode: the case count belongs to the
installed suite rather than to the specification, and runners column-align their summaries
(`valid tests: 205 passed,  0 failed` carries two spaces), so a literal such as
`assert "valid tests: 210 passed, 0 failed" in result.stdout` is false on correct code and no
implementation can move it. The same holds for tallies of errors, skips, and warnings: a runner
with none of them commonly prints no such line at all, so requiring one is false on a clean run.

Print the captured output for diagnosis, assert `result.returncode == 0`, and stop there. This
holds for both `Suite: scoped` and `Suite: full`.

Place a whole-project deterministic suite on the story that **completes the runnable capability**
— never on a foundation step that cannot yet run it, where it would fail vacuously. Naming the suite file or asserting it is staged (`Path(...).is_file()`)
is staging, not testing: a stubbed or absent definition of done for an available suite is a defect,
not an acceptable check.

An assertion that invokes a staged asset obeys that asset's own documented interface. Read the
asset before writing the call. Every environment variable it declares required is supplied, and it
is supplied by extending the inherited environment — `env={**os.environ, "NAME": value}`. Never
write `env={"NAME": value}`: that replaces the environment, leaving the child with no `PATH`, so
nothing it invokes resolves and the assertion fails at every level of implementation quality. Never
repair a staged asset's interface by editing the asset; it is restored before grading, so the edit
is reported as tampering rather than honored.

An assertion that feeds input to a program passes it through `subprocess` `input=` rather than a
shell. When a shell is unavoidable, `printf '%s'` copies its argument verbatim: `\n` reaches the
program as a backslash and a letter, not a newline, so the program is graded on input the author
never wrote. Use `printf '%b'` or a real line break.

`COMPASS.md` uses `## Compass`, `## Constraints`, and `## Guardrails` as its body sections.
Success criteria belong in `SEA_TRIALS.md`; open questions in spike questionnaires. Do not add
those sections to `COMPASS.md`.

## Acceptance Criteria Files

**Naming rule:** any file where `AC` is a whole word in the filename is an acceptance criteria
file. `AC` must be delimited by `-`, `_`, or file boundaries — not embedded in another word.
Examples: `AC-001-login.md`, `FEATURE-LOGIN-AC.md`, `AC-NAVIGATION.md`.
`ACCEPTANCE_CRITERIA.md` does NOT follow this standard (AC is not a standalone word).

AC files enable test-driven design and a way to enforce specific behaviors without polluting the
parent specification.

**Two types of AC statements:**

| Type | Example | Rule |
|------|---------|------|
| Positive assertion | "The status badge color is red" | Reconcile into parent spec, then archive this entry |
| Negative/guardrail | "Field X must not appear on this screen" | Keep permanently in AC — these guard against model hallucination, not spec omission |

**Reconciliation:** When a positive AC fact has been implemented and verified, move it to the
parent spec body and delete the AC entry. Negative guardrails are permanent — never move them to
the spec.

**AC file format:**

```markdown
# AC: {ObjectName}

| Field       | Value |
|-------------|-------|
| Version     | YYYYMMDD V1 |
| Description | Acceptance criteria for {ObjectName}. |
| Parent      | FEATURE-{Name}.md |

## Guardrails

- Field X must not appear on this screen.
- The delete button must not be shown to read-only users.

## Assertions

- The status badge is rendered in red when severity is HIGH.
```

**Standard AC filename forms:**
- `AC-NNN-{Name}.md` — numbered sequential acceptance-criteria ticket (authored)
- `{Parent}-AC.md` — paired directly with a spec file (e.g. `FEATURE-LOGIN-AC.md`)
- `AC-{Topic}.md` — topic-scoped AC file (e.g. `AC-NAVIGATION.md`)

**All fix and change tickets use AC naming** — `AC` as a whole word in the filename. A targeted
bug fix is expressed as a testable acceptance criterion.

| Convention | Rule |
|------------|------|

## Acceptance Strength

A criterion states one expectation. Pin the status the implementation answers with: a stub that
answers `200` is a real contract and a real test, and specifying a stub is legitimate.

`404` means the endpoint is absent. Asserted alone it is a deliberate negative probe and one of the
strongest checks available. Admitted beside any other status it makes the criterion true of an
application that implements nothing, so `in {200, 404}` and `in {400, 404}` are both defects. A set
admitting both success and a `5xx` is a defect for the same reason.

A criterion that needs a row to exist creates it through the public interface first. Admitting the
status that says the row never existed is not a substitute for building the state the criterion
depends on.

## Persistence Encapsulation (DATABASE.md scope)

`DATABASE.md` is the project's persistence contract — not SQL schema alone. It documents every
persistent store and the typed repository contract that encapsulates it:

- **Relational stores** — declared tables, the access patterns that reach them, and their DTO
  inputs and outputs. Drydock generates the implementation from this; no Blueprint describes one.
- **Config / `.env`** — required keys and the typed `Config` class.
- **File stores** — directories and the `FileStore` class.
- **External services** — the service contract and its wrapper.

Routes call services; services call the generated persistence package — `db.<table>.<verb>(...)`,
one method per declared access pattern. SQL, sessions, table names, and column names never cross
that boundary, and no Blueprint describes a repository implementation: Drydock generates it from
this declaration. A storage change that leaves the named
repository-call contract unchanged does not invalidate downstream features.

Every `DATABASE.md` includes `## Access Patterns` before schema details. Every access pattern has a stable feature-owned `FEATURE-<DOMAIN>-<NNN>` id, Owner,
`read`, `write`, or `read-write` access, repository method, DTO input and output shapes, and
compatibility level: `unchanged`, `data`, or `rebuild`. Route and screen Blueprints cite only those
ids through a `## Database Interface` section, including only fields they supply or receive; they
do not cite a physical store. Persistence interfaces name the repository, module location, and
allowed callers.

A Feature cites only access patterns whose Owner names that exact Feature or the shared owner
`DATABASE.md`. When several Features use an operation, declare the shared owner in `DATABASE.md`;
never claim another Feature's private pattern. Derive each interface's DTO field list from the
current `DATABASE.md` rather than from a remembered draft.

`## Database Interface` is required, not optional, for every Blueprint that `DATABASE.md` names
as the `Owner` of an access pattern. Ownership is read from the declaration, never guessed from a
story's `stack:`: a stack selection says which technology the story is built with, not whether it
reaches a repository. Each citation is one bullet on one line, in this exact form:

```text
## Database Interface

- `FEATURE-ORDER-001` — write: create an order - supplies: `customer_id`, `items` - returns: `id`, `status`
- `FEATURE-ORDER-002` — read: retrieve an order by id - supplies: `order_id` - returns: `status`, `total`
```

The id is an `## Access Patterns` id in backticks, the em dash is literal, the access is `read`,
`write`, or `read-write`, and `supplies:` and `returns:` carry comma-separated backticked field
names from that pattern's Input and Output DTOs. Author an empty list explicitly as `—`:
`- supplies: — - returns: —`. The reader also accepts an omitted `supplies:` or `returns:`
as an empty claim when the other field clause is present. Required inputs, declared fields
and access grants remain validated against DATABASE.md; omission never supplies a required input.
A Blueprint that reaches no repository — a Screen
that delegates to a Feature's service routes — writes one bullet and no other:

```text
- None — persistence is owned by FEATURE-ORDER.md.
```

`- None` is available only to a Blueprint the declaration names nowhere. A Feature named as an
`Owner` states the operations it owns, or the `| Owner |` row moves to the Feature that does own
them. A pattern owned by `DATABASE.md` is shared: any Blueprint may cite it, and none is required
to.

Every bullet under the heading is an entry and every entry is checked, so a sentence of prose there
fails the plan as a malformed citation. Say it in `## Purpose` instead. A citation may claim less
access than the pattern grants — a read-only consumer of a `read-write` surface is a real claim —
but never more. Drydock checks each citation
against the declaration. An unknown operation, a wrong owner, access the pattern does not grant, a
field the DTO does not carry, or a required field left out is a conflict Build would implement, and
it fails the plan. A Blueprint whose story selects a persistence stack and cites nothing fails it
the same way. Persistence is the one part of a plan decidable from the artifacts alone, so none of
it is left to a Commander to answer: Drydock repairs the cited Blueprint and re-validates, and a
defect that survives repair stops the run.

Each access pattern is its own `### FEATURE-<DOMAIN>-<NNN> — <Operation>` section over a
`| Field | Value |` table carrying Owner, Access, Repository operation, and Compatibility, followed
by an `Input: <DTO>` and an `Output: <DTO>` field table. Never collapse the operations into one
table of rows.

An Output DTO name has one ordered field/type definition throughout `DATABASE.md`. Reuse a
name only for the same record shape. For a distinct projection, derive a descriptive name
from the complete repository operation: `rates.get` becomes `RatesGetOutput`, and
`rates.delete` becomes `RatesDeleteOutput`. The latter may carry only `date` and `currency`
while the former also carries `rate`; they never both use `Rate`. Preserve the required fields
and caller expectations when repairing a name conflict. Do not add a field to a delete output
merely to match another DTO, and do not add arbitrary numeric suffixes. Python class-name
normalization also applies: spellings such as `Rate` and `R-ate` name the same generated class.

`Owner` is the file name of the Feature that reaches this pattern — `FEATURE-ORDER.md` — and
never a service, module, or layer name. Only a Feature owns data: a Screen renders it through a
Feature's service and never holds a repository. It is the only place the plan says which Feature
owns which data, so it is compared to the emitted file names rather than read as prose: an Owner
naming something that is not a Feature in this plan fails the plan, as does a Feature that owns a
pattern and cites nothing.

A pattern no single Feature owns — an activity log or other shared surface several Features write
and several Screens read — names `DATABASE.md` as its `Owner`. That states the fact: the data is
declared here and no Feature claims it. Any Blueprint may cite a shared pattern, no Blueprint is
required to, and `DATABASE.md` cites nothing itself. Never invent a Blueprint file name for a
surface that has no Feature; name `DATABASE.md` instead.

`Repository operation` names one declared table and one operation as `<table>.<name>`,
lowercase snake_case: `` `settings.get` `` or `` `rates.replace_rate` ``. The name is the method
callers use, `db.<table>.<name>(...)`, and it is the contract they depend on. Its `| Kind |` row
says how it runs: `get`, `list`, `create`, `update`, `upsert`, or `delete`, and no other. A name
that is itself one of those words is its own Kind and needs no Kind row, so a simple table
declares `rates.get` and `rates.update`. Any other name declares its Kind:

```markdown
| Repository operation | `rates.reprice_currency` |
| Kind | update |
| Match | `currency` |
```

One access pattern declares exactly one operation, because it carries exactly one `Input:` and
one `Output:` table — a cell naming two operations leaves which fields belong to which
undeclared. Give each operation its own `### <FEATURE-DOMAIN-NNN>` section with its own DTO
tables. A table may hold several operations of one Kind under different names, such as
`rates.update` by `PK` and `rates.reprice_currency` by currency. Each name is declared once, and
two names that run the same Kind, Match, Sets, and Output are synonyms: declare one and cite it
everywhere.

An optional `| Match | `a`, `b` |` row names the Input fields that select the rows an operation
reaches. Every Match field is an Input field, required at call time except on a `list`, and the
terms are joined with AND. A bare field is compared by equality with the column of its own name.
A term `<column> <op> <field>`, with op one of `=`, `<`, `<=`, `>`, `>=`, compares an Input field
that is not a column with that column, so a range is two terms on one column:
`` `date >= start_date`, `date <= end_date` ``. A comparison term belongs to a `list`, `update`,
or `delete`; `get` and `upsert` match a unique key by equality. Every Input field is a column of
the table or the field of a comparison term, and a field appears in one term only. No other
operator, no OR, no join, and no SQL exist. A Match whose equality fields cover the `PK` or a
declared `UNIQUE` reaches at most one row; any other Match reaches many. Each Kind uses Match
exactly as follows:

| Kind | Match | Input fields | Rows | Returns |
|---|---|---|---|---|
| `get` | a unique key; defaults to every Input field | exactly the Match | 0..1 | the Output row, or none |
| `list` | optional; states how each filter compares, and every filter, bound included, is optional | the filters | 0..n | a list of Output rows |
| `create` | not declared | the values inserted | 1 | the Output row |
| `update` | any Input fields; defaults to the `PK` | the Match plus at least one column to set | 0..1 on a unique key, else 0..n | the Output row, or none; a count when it reaches many |
| `upsert` | required; exactly one declared unique key | the Match plus the columns to set, including every `NOT NULL` column without a `DEFAULT` | 1 | the Output row |
| `delete` | defaults to every Input field | exactly the Match | 0..1 on a unique key, else 0..n | the Output built from the Match, or none; a count when it reaches many |

A `list` returns its rows in no stated order unless it declares `| Order | `date` asc |`: one or
more columns of the table, each `asc` (the default) or `desc`, the first the primary sort key.
Declare an Order whenever a story states one, such as "points in ascending date order"; Order
belongs to a `list` only.

```markdown
| Repository operation | `rates.history` |
| Kind | list |
| Match | `currency`, `date >= start_date`, `date <= end_date` |
| Order | `date` asc |
```

An `update` or `delete` that reaches many rows declares its Output with no fields, because it
returns the number of rows changed. `upsert` inserts the row its Match identifies, or replaces
that row's other Input columns when it exists, in one atomic statement. It is the operation for a
source rule such as "a stored (date, currency) is replaced". A `get` on a non-unique field is a
`list`. A pattern that breaks one of these rules fails the plan with the rule named.

```markdown
### FEATURE-RATE-004 — Store a rate, replacing the stored one

| Field | Value |
|-------|-------|
| Owner | FEATURE-RateStorage.md |
| Access | write |
| Repository operation | `rates.replace_rate` |
| Kind | upsert |
| Match | `date`, `currency` |
| Compatibility | unchanged |
```

Drydock derives each operation's contract from the declaration: its call, Kind, Match, Sets,
rows, Input and Output as JSON with caller types (`str`, `int`, `float`, `bool`, `bytes`), the
SQL the runtime executes, and a contract fingerprint. Only a change a caller can see moves the
fingerprint: the name, Kind, Match terms, Order, rows, return shape, or a field's name or caller
type. A
column's length, nullability, `DEFAULT`, an index, or the SQL never does, so changing them
rebuilds nothing beyond `DATABASE.md`. It is the only place the declaration says which table a pattern reaches, so the form is
checked rather than advisory, and free text there fails the plan. Every table in `## Schema` is reached by at least one access
pattern, and every operation names a table `## Schema` declares. A table nothing reaches is
storage no story can use; an operation on a table that is not declared builds a repository against
nothing. Declare the pattern in the same batch as the table. A `DATABASE.md` whose `## Access Patterns` holds no named operation fails the plan:
Build reads that surface to fingerprint the persistence contract, and an unparseable one stops the
build after a block has already been spent.

`DATABASE.md` is authored in one step: its own Blueprint batch, complete, and then frozen like
every other Blueprint. That batch starts from a seed of the Rigging template and every table the
imported source specification already declared; keep every seeded table. Declare every table and
one access pattern for each repository operation any story in the frozen topology needs. Later
batches receive the frozen declaration as `DATABASE_compact.md` and cite its access patterns. Its
generated `## Operation Surface` gives, per table, each operation's contract: call, Kind, Match,
Sets, rows, Input and Output JSON, and SQL. Author criteria and callers against it.

Each table is a top-level `` ## `table_name` `` section — lowercase snake_case in backticks — over
a `| Field | Type | Notes |` table. A type cell is
`<TYPE> [PK] [NOT NULL] [UNIQUE] [DEFAULT <literal>] [REFERENCES <table>(<column>)]`, where
`<TYPE>` is `INTEGER`, `TEXT`, `REAL`, `NUMERIC`, or `VARCHAR(<n>)`, and `<literal>` is a
single-quoted string, a number, `NULL`, `CURRENT_TIMESTAMP`, `CURRENT_DATE`, or `CURRENT_TIME`.
Brackets mark optional entries and are not written: `TEXT NOT NULL UNIQUE`, never
`TEXT NOT NULL [UNIQUE]`. Nothing else is accepted: Drydock renders executable DDL from these cells, so a modifier it cannot
read is a constraint the built database would not have. Declare a length where one matters —
PostgreSQL enforces `VARCHAR(<n>)` and SQLite accepts the same declaration and ignores it, so one
spelling serves both. A foreign key names a table and column this same file declares.

Every table declares exactly one `PK` column, such as `| id | INTEGER PK | |`. A natural key
spanning several columns, such as `(date, currency)`, is a `- UNIQUE (date, currency)` bullet
beside the `PK`, never a second `PK`. An operation reaches a row by its natural key through
`| Match |`, so declaring the `UNIQUE` is what makes `get`, `update`, `upsert`, or `delete` by
`(date, currency)` reach exactly one row. A table with no `PK` column, or with two, fails the plan.

A constraint spanning more than one column cannot live in a per-column row, so it is declared as a
bullet directly under that table's field table, one per line:

Build implements the declaration, and an empty one leaves Build inventing a schema no Blueprint
describes.

Relational persistence needs no ORM or migration-framework selection in the Technology Stack.
Drydock generates the persistence package from this declaration at the DATABASE build step and
copies the engines in unchanged, so a story that implements `DATABASE.md` writes callers, not a
repository. A Target declaring a `DATABASE.md` in a language Drydock ships no adapter for fails

migration ledger record lives at `blueprint/migrations/MIGRATION-<AccessPatternId>.md`; it holds
`upgrade` and `downgrade` snippets and is `planned` until the DATABASE build story completes, then

# Build Instructions: A Currency Rates Service

## Objective

Build a small web service that keeps the European Central Bank (ECB) euro reference exchange
rates and answers questions about them: the rates on a date, a currency conversion, and a
currency's history over a period. A command-line tool loads the ECB's published history file into
a local database. A JSON HTTP API serves the answers.

## Stack

Implement in Python 3.11 or newer with FastAPI, served by uvicorn, over SQLite. Tests run under
pytest, using FastAPI's `TestClient` for the API. The product is an executable named `fxrates` at
the application root.

## Run Harness

`sources/run.sh` is the scoring entry point. It is supplied, not authored, and is staged verbatim
into the application root with the data files. `drydock uat` runs `sh sources/run.sh` from the
completed application root and takes its exit code and output as the score.

The harness sets `DATABASE_URL` to a fresh temporary SQLite file, runs `./fxrates init` and
`./fxrates load`, starts `./fxrates serve --port <port>` in the background on a free local port,
waits up to 30 seconds for `GET /health`, and then runs HTTP requests against `127.0.0.1`. It
makes 35 checks. A command check compares exit code and standard output. An HTTP check compares
the status code and, for status 200, the JSON body as a value (key order and whitespace do not
matter). Standard error and error-response bodies are never compared. The harness never runs
`fetch` and uses no network beyond `127.0.0.1`. It prints `PASS` or `FAIL` per check and ends with:

```text
FxRates: NN passed, NN failed (of 35)
```

## Read-only scoring assets

These files are the exam. Do not modify, rewrite, regenerate, or substitute them:

- `sources/run.sh` — the scoring entry point and its known answers
- `sources/eurofxref-hist_2025-01.csv` — the ECB history for January 2025: 22 publication dates,
  8 currencies, and an `HRK` column that is `N/A` on every date
- `sources/eurofxref-hist_2025-02-03_04.csv` — two further dates, 2025-02-03 and 2025-02-04

the database.

## Database

`DATABASE_URL` names the SQLite database file, optionally prefixed `sqlite://`. When it is unset,
`DATABASE_PATH` is used, then `data/app.db`. All database access goes through the shipped
persistence library and the relational layer generated from `DATABASE.md`. Application code never
opens a database driver directly.

One table:

| Table | Columns | Keys |
|---|---|---|
| `rates` | `date` text `YYYY-MM-DD`, `currency` text, `rate` text | unique (`date`, `currency`) |

A rate is stored exactly as the ECB publishes it, as text. `0.943` stays `0.943`, never `0.9430`
and never a float. Arithmetic on rates uses Python's `decimal` module.

## Command line

| Command | Behavior | Standard output |
|---|---|---|
| `fxrates init` | Drops the `rates` table if present and creates it empty. | Nothing. |
| `fxrates load <csv>` | Loads an ECB history file (rules below). | `dates,rates`, then the number of dates and of rates stored from the file. |
| `fxrates fetch` | Downloads `https://www.ecb.europa.eu/stats/eurofxref/eurofxref-hist.zip`, extracts `eurofxref-hist.csv`, and loads it as `load` does. | As `load`. |
| `fxrates serve [--port <n>]` | Serves the HTTP API on `127.0.0.1:<n>` with uvicorn until stopped. Default port `8000`. | Nothing required. |

**ECB history file rules.**

1. The file is CSV. The header's first field is `Date`, and every other field is a three-letter
   uppercase currency code. The ECB writes a trailing comma on every line, and the resulting
   empty last field is ignored.
2. Each row is a date (`YYYY-MM-DD`, a real calendar date, not repeated within the file) followed
   by one value per currency. The value `N/A` means no rate, and nothing is stored for it. Any
   other value must match `[0-9]+(\.[0-9]+)?` and be nonzero.
3. **A rejected file changes nothing.** The whole file is checked before the first write. A row
   with the wrong field count, an invalid or repeated date, or an invalid value rejects the file.
4. A rate for a (`date`, `currency`) that is already stored replaces it, so loading the same file
   twice leaves the database unchanged.
5. The reported `dates` counts the dates with at least one stored rate, and `rates` counts the
   rates stored.

A failing command writes nothing to standard output and one diagnostic line to standard error.
`fetch` is never run by the harness. Its tests replace the download with a stub and never use the
network.

**Exit codes.** `0` success. `1` operational failure: the file cannot be read, or a `fetch`
download fails. `2` usage error: unknown command, wrong argument count, `--port` not an integer.
`3` rejected file.

## HTTP API

Every response is JSON. EUR is the base. A rate is the number of units of a currency per euro, and
EUR itself has the implicit rate `1`.

**Effective date.** The ECB publishes on working days only. A request for date `D` uses the latest
publication date on or before `D`. If none exists, the response is `404`.

| Request | Status 200 body |
|---|---|
| `GET /health` | `{"status": "ok"}` |
| `GET /stats` | `{"dates": <n>, "rates": <n>, "first": <date>, "last": <date>}`. `first` and `last` are `null` when the table is empty. |
| `GET /currencies` | `{"base": "EUR", "currencies": [<code>, ...]}`: every currency with at least one stored rate, ascending. |
| `GET /rates/{date}` | `{"date": <effective date>, "requested": <date>, "base": "EUR", "rates": {<code>: <rate>, ...}}`: every currency with a rate on the effective date. |
| `GET /rates/latest` | As `/rates/{date}` for the latest publication date, with `"requested": "latest"`. |
| `GET /convert?from=<code>&to=<code>&amount=<amount>[&date=<date>]` | `{"date": <effective date>, "from": <code>, "to": <code>, "amount": <amount>, "rate": <rate>, "result": <result>}`. Without `date`, the latest publication date is used. |
| `GET /history/{code}[?start=<date>][&end=<date>]` | `{"currency": <code>, "base": "EUR", "count": <n>, "min": <rate>, "max": <rate>, "mean": <mean>, "points": [{"date": <date>, "rate": <rate>}, ...]}` for the publication dates from `start` through `end` inclusive, ascending. Both bounds are optional. With no points, `count` is `0`, `min`, `max`, and `mean` are `null`, and `points` is `[]`. |

**Values.**

- `<rate>` in `/rates`, `min`, `max`, and `points` is the stored text, as a JSON string.
- `/convert` `amount` matches `[0-9]+(\.[0-9]+)?` and is echoed as given, as a JSON string.
- `/convert` `rate` is `rate(to) / rate(from)`, computed exactly and rounded half to even to six
  decimal places, written with exactly six decimals, as a JSON string: `"161.770000"`.
- `/convert` `result` is `amount × rate(to) / rate(from)`, computed exactly from the stored rates
  (not from the rounded `rate`) and rounded half to even to two decimal places, written with
  exactly two decimals, as a JSON string: `"82.01"`.
- `/history` `min` and `max` are the stored text of the smallest and largest rate by value.
  `mean` is the exact mean rounded half to even to six decimal places, written with exactly six
  decimals, as a JSON string.

**Errors.**

| Status | Condition |
|---|---|
| `404` | No publication on or before the requested date; a `/convert` currency other than EUR with no rate on the effective date; a `/history` currency with no stored rate at all (including `EUR`). |
| `422` | A malformed date in the path or query, a malformed `amount`, or a missing required query parameter. FastAPI's request validation produces this status. |

A load that completes while the server is running is visible to the next request.

except Exception as e:

    print(f"status: expected {want}, got {status}")

    sys.exit(0)
try:

except ValueError:

expected = json.loads(open(want_file, encoding="utf-8").read())

    print("got:     ", json.dumps(got, sort_keys=True))

Manifest Construction Rules

Derive the Manifest from the authored specs, not directly from the imported source text.

Story types

  • One story per governed specification: implements: names exactly one spec file, and every

authored spec file is implemented by exactly one story. The story is the atomic build primitive.

  • foundational — structure and scaffolding. Standing up S3 and proving the connection is

architecture. Recognizing that something must establish the web server, and making it a node, is your judgment and determines story structure.

  • service — everything that does work. Much of what source material labels architecture is

service work: the web server and the database are foundation; a voice service interpreter is a service wearing an architecture filename.

  • feature — an assembly story. It depends on its member stories, carries acceptance criteria, and

carries assembly and intent instructions instead of implementation instructions. It is not a grouping construct and it is not a batching unit.

  • There is no fourth type, and no spike or ac story type. A research question becomes a

questionnaire before Plan or a DECISIONS.json record after.

Story sizing

  • A story is a normal Agile story: 1 to 5 story points. Never a half point — that is a task,

and a task is folded into the story it serves. Never twelve — that is split.

  • A story does one thing completely, carries test criteria, and is releasable on its own. A task is

not releasable and is therefore not a story.

  • Size by that judgement alone. A story has no token dimension: token cost is a property of the

block a story is built in, not of the story.

  • Story count is not capped, and it is an output of correct decomposition rather than a target.

Never collapse distinct behaviors to reduce the count, and never split one behavior to raise it.

Stack

  • Draw stack: values from the Rigging column of TECHNOLOGY_STACK.md: give each story the files

for the technologies it actually builds with, and no others. A technology whose Rigging cell is — contributes no stack: entry. When TECHNOLOGY_STACK.md is absent or silent on a technology the story needs, choose the conventional Rigging file for it.

  • Never emit stack_mode:. Drydock assigns builder/consumer from first use in the order it

computes.

  • Any story that implements DATABASE.md must include persistence.md in stack: plus the

selected backend stack file such as sqlite.md, postgres.md, or aws-dynamodb.md.

Context

  • Use context: only for genuine read-only support files.
  • For context files classified in ANALYSIS.md ## Source Roles, preserve their source role in

a context_roles: | mapping (<path>: <role>). Key it by the promoted Blueprint name, never a sources/... path. A test suite or harness is context, never implements.

  • A file the Analysis marks stage is present in the build directory at sources/<name>.

Reference it by that build-relative path in Programmatic Acceptance. Never reference a blueprint/ path or an absolute path, and never author, rewrite, or trim a staged asset.

Decisions

  • Where the Blueprint, guardrails, or stack declaration are silent on a needed decision, decide:

pick the option that most reduces rework risk, proceed as if it were chosen, and disclose it as a DECISIONS.json item (see Significant Design Decisions below). Ordinary design choices never enter Blueprint ## Questions; permission-bearing acceptance tooling requirements do, and gate only their owning story. Assign low, material, or blocking severity. Ordinary Plan-selected choices never hard-block regardless of severity.

  • Treat counts, summaries, indexes, and other derived metadata as subordinate to the detailed

records from which they are computed. When derived metadata disagrees with an unambiguous detailed enumeration, recompute it from that enumeration and continue. This is neither a product question nor Error Mode. Do not require the Commander to correct a stale derived total.

Acceptance

  • Durable behavioral acceptance lives in the implemented spec's Programmatic Acceptance: a SCREEN

spec's assertions call every route the screen provides and consumes; a FEATURE spec's assertions exercise every route, interface, read, and write it provides.

  • Do not copy Sea Trial commands into ordinary story acceptance or execute them while planning.
  • The terminal story is the last story in the build order — the one on which every other story

is a transitive dependency and after which no further story runs. Position in the dependency graph decides it, never the story's name, type, or kind. A story that stages the test assets runs first and is never terminal. Resolve depends and identify the terminal story before writing any suite criterion.

  • When the Analysis states a terminal verification story, that one story gates on the complete

suite: its Programmatic Acceptance assertion declares Suite: full as one of the block's declaration lines, and it depends on every implementation story. Without that declaration a full-suite run is rejected. Only the terminal story runs the whole suite.

  • A story that owns behavior the suite covers gates on its own slice: the runner scoped by its

selector to the cases that story implements, executing them, asserting exit 0. Declare the runner's list-mode selector as Probe: and its output format as Probe Count:; Drydock runs the selection probe during verification. Do not execute tools or invent a selected count while authoring the plan. An unbounded run of the suite from any non-terminal story, without Suite: full, is rejected.

  • A pure harness staging story — one that proves the runner is staged and starts, implements none

of the behavior under test, and gates no correctness — is the single exception: it invokes the runner in its list or dry-run mode, which enumerates the suite without executing a case, and asserts the runner exits 0 and reports the expected count. Using list mode anywhere else produces a criterion that is green before the code exists. Never leave a staging story with no criterion: a story that cannot be verified closes advisory and gates nothing.

  • Every invocation of a staged asset — in any story, in any mode, including list and dry-run mode —

supplies every environment variable that asset declares required, by extending the inherited environment (env={**os.environ, "NAME": value}). Read the asset's usage block for the value it names. An asset that is called without a variable it requires exits on its own usage code, which is a harness fault and never a verdict about the product, so the criterion is false under every implementation and no build can move it.

  • When an authoritative conformance suite is imported (a specification's example set plus its

runner), every implementing feature story binds its acceptance to that suite over the sections it owns, never to a hand-written sample. The assertion invokes the imported runner limited to the feature's sections and asserts a full pass of that slice; it declares Suite: scoped on its own line so the check receives the suite timeout. Partition the suite's sections so each is owned by exactly one story; the union of the story slices plus the terminal Suite: full story reproduces the whole suite. One story owning every section is an under-decomposed plan. A scoped run requires runner success and zero failures/errors within its selected slice. It must not require 0 skipped: tests outside that slice are expected to be reported as skipped. Only the terminal Suite: full assertion may require zero skipped tests.

  • Absent such a suite, every non-terminal story stays bounded — a hand sample proves a unit works,

never that the project is correct.

Ordering and grouping — not yours

  • Do not sort the stories. Do not compute a topological order. Do not group them into batches.
  • Do not emit block:. Blocks are ephemeral context-optimization groups computed by Drydock: one

topology type per block, never crossing a phase boundary, never violating the edges, packed to amortize stack-file cost across one build pass. Context economy comes from blocks, not from feature grouping. Only stories ready before a block starts can share it; a dependent story is built and graded after its prerequisites, never in their agent call.

  • Declare depends: as genuine input requirements only. An entry that is decoration rather than a

real prerequisite corrupts the order Drydock computes from it.

Acceptance persistence lifecycle

Acceptance store lifecycle. The DATABASE step provisions and verifies the configured store once. Ordinary persistence criteria never replace DATABASE_URL/DATABASE_PATH, create a temporary database, apply DDL, or assume an empty store. Configuration behavior is tested separately using the harness fixture below. The store may hold data before any criterion runs: assert on records the criterion created, or on a count read before setup (after == before + 5), never on an absolute table count.

SQLite configuration tests (Python acceptance container). The harness supplies from drydock_acceptance import database_environment. Use it only to test configuration selection, default paths, or source-required open failures, never ordinary CRUD acceptance:

import os
from drydock_acceptance import database_environment
from <declared_config_module> import database_path

with database_environment(url="sqlite://primary.db", path="fallback.db") as root:
    assert str(database_path()) == str(root / "primary.db")
with database_environment(path="fallback.db") as root:
    assert str(database_path()) == str(root / "fallback.db")
with database_environment() as root:
    assert str(database_path()) == "data/app.db"

None (the default) unsets a variable; "" sets it empty. Other arguments are relative SQLite file names within a fresh temporary working directory; only url permits the sqlite:// prefix. The fixture maps names to absolute scratch paths, yields that directory as a Path, and restores both variables and cwd on exit, including failures. It applies no schema and creates no parent directories: url="missing/app.db" exercises an unopenable path. Invoke the declared application interface inside the context, assert the source-required outcome, and do not read or write the managed store. Import the declared configuration module, never invent a module or an exit requirement absent from the source. Do not replace environment variables directly or bypass this fixture with monkeypatches.

For acceptance-store repair of an existing configuration test, move its environment setup and restoration into this fixture. Preserve URL-prefix/precedence/unset/empty conditions, command arguments, error behavior and expected results. Replace arbitrary fixture paths with relative names and derive asserted absolute paths from root; this is a mechanical fixture relocation, not permission to change which configured value wins or weaken any assertion. If the criterion needs a populated replacement store, report REPAIR_IMPOSSIBLE instead.

The acceptance harness owns isolation. It begins one transaction before each Python criterion and rolls it back when the criterion ends, pass or fail. Every database the criterion's process opens joins it: db_session(), the application behind web_client(), and commands run through cli_runner(). Setup, behavior and readback therefore see one another's writes, and none persists; leaving a with db_session() as db: block rolls nothing back. Seed with with db_session() as db: and pass that database into feature operations. Never commit, clean up, or open a transaction.

A criterion that launches a process (subprocess, a server on a port, a shell script) cannot see that transaction. It does not open the store and does not depend on rows it wrote; exercise stored behavior in-process instead. Go criteria use OpenSession(ctx, "") with checked deferred cleanup, which rolls back its own transaction. Go HTTP, CLI and restart criteria use OpenCommittedSession(ctx, "") with a criterion-owned identifier and checked defer cleanup through supported product interfaces. Database acceptance must not be replaced by a project test count: runtime catalog and row-count evidence proves provisioning, feature criteria prove behavior.
