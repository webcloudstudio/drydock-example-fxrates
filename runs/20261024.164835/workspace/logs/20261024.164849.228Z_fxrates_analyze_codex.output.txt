## Story List

### Feature: ECB Rate Data

| ID | Story | High-level AC |
|---|---|---|
| ECB-001 | Initialize the rate store | `fxrates init` drops any existing rates table and creates an empty one. |
| ECB-002 | Load ECB history files | Load validates the complete CSV before writing, skips `N/A`, stores published rates as text, replaces matching date and currency rates, and reports date and rate counts. |
| ECB-003 | Fetch and load ECB history | `fxrates fetch` downloads and extracts the ECB history file, then loads it using the same rules as the file loader. |
| ECB-004 | Report store statistics and currencies | API callers can retrieve date and rate counts, first and last publication dates, and the sorted currencies with stored rates. |

### Feature: Rates and Conversions API

| ID | Story | High-level AC |
|---|---|---|
| API-001 | Report service health | `GET /health` returns `{"status":"ok"}`. |
| API-002 | Retrieve rates by effective date | `GET /rates/{date}` returns all rates for the latest publication on or before the requested date, or 404 when none exists. |
| API-003 | Retrieve the latest rates | `GET /rates/latest` returns rates for the latest publication and identifies the request as `latest`. |
| API-004 | Convert between currencies | `GET /convert` resolves the effective date, computes the cross-rate and result from exact stored values, and returns the required decimal strings. |
| API-005 | Retrieve currency history | `GET /history/{code}` returns the currency's points within inclusive optional bounds, with count, extrema, and rounded mean; an empty range returns empty statistics. |
| API-006 | Validate API requests | Malformed dates and amounts, and missing required parameters, return 422; unknown or unavailable currencies return 404. |

| CLI-002 | Report command failures and usage errors | Commands use the specified exit codes, write no standard output on failure, and write a diagnostic line to standard error. |

## Planning Instructions

### Delivery Shape

Deliver a Python command-line executable and a local FastAPI JSON service backed by SQLite through the shipped persistence library and relational layer generated from `DATABASE.md`. The inputs are ECB history CSVs or the ECB history ZIP; outputs are persisted rate records, command results, and JSON responses. The primary flow initializes the store, loads history, starts the service, then serves rates, conversions, and history requests. Fetch uses the same load behavior as file loading.

### Test and Acceptance Strategy

Use focused story tests for command behavior, file validation, API responses, effective-date resolution, decimal arithmetic, and errors. Stub the fetch download in automated tests so tests make no network connection. Run `sources/run.sh` unfiltered as the terminal acceptance gate; it exercises the complete supplied grader and must exit zero.

### Sequencing and Dependencies

Establish the generated relational layer and persistence library before store-backed commands or routes. Implement initialization and atomic loading before the API capabilities that read rates. Implement fetch using the completed loader. Build the service and CLI serving command before API acceptance. Build focused automated tests alongside their behavior; the automated suite runner follows those tests. VERIFY-002 depends on all implementation stories and runs the staged grader with its staged data files.

### Source Conflicts and Gaps

The sources define both CLI commands and programmatic HTTP routes with no human-facing screens, so the project type is mixed (`ambiguous`). No source conflict requires a Commander decision. The service has no stated authentication requirement; the described API is a local service bound to 127.0.0.1. Fetch behavior is specified, but its failure details beyond exit code 1 are not further constrained.
